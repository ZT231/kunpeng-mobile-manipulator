## 二、🔴 CubeMX 要不要改？**这次不用改**（你问的那条，明确回答）

| 问题 | 结论 |
|---|---|
| `1.Smart car` 有 `.ioc` 吗？ | **没有**。它是 **Keil MDK + 标准外设库（SPL）** 工程（`demo.uvprojx` + `RTE/Device/STM32F407ZE/`），从头到尾就没用过 CubeMX。所以「改 CubeMX」在这份固件上**无处可改**。 |
| 4 号项目的 `.ioc` 是谁的？ | `RoboticArm_Kunpeng.ioc` = **机械臂板 STM32F407VE**（CubeMX + HAL + FreeRTOS），已配 USART1/2/3、I2C1、ADC1、DMA、TIM6。它是另一个 MCU 节点。 |
| 架构允许两块板吗？ | **本来就是两块板**。`docs/机械臂小车+语音-可行性与落地路线.md` 第六节架构图明确画的是「底盘 F407ZE」与「机械臂 F407VE」两个独立节点，鲲鹏作为边缘协调器统一发 `$<CMD>*<CK>`。所以底盘固件完全不碰机械臂的 `.ioc`。 |
| 什么情况下**才**需要改 CubeMX？ | 只有当你想把车和臂**合并到同一块 F407VE** 上时才要：得在 `.ioc` 里加 TIM8（PC6~PC9 四路 PWM 给 L9110S）、HC-SR04 的定时器/外部中断、循迹 GPIO，还要把小车串口从已被占用的 USART1 挪走。代价是 **Generate Code 重新生成 + 重烧固件**（重烧会甩臂）、并且会动到已实机验收的机械臂链路 ⇒ **不推荐，本次不做**。 |

**概念补一句（大白话 + 规范定义）**：
- **CubeMX** 是 ST 官方的图形化配置工具，用鼠标点引脚 / 时钟 / 外设，它自动生成 HAL 初始化代码；它的工程配置存在 `.ioc` 文本里（ST 官方文档：STM32CubeMX / STM32Cube HAL）。
- **标准外设库 SPL** 是 CubeMX 之前的老一套寄存器封装（`GPIO_InitTypeDef`、`RCC_APB2PeriphClockCmd` 这些就是 SPL 的写法），工程文件是 Keil 的 `.uvprojx`。两套库**不能混用**，所以「合并」只能按节点各自保留，不能把 SPL 驱动直接塞进 HAL 工程里编。

## 三、统一帧协议（与机械臂 `Core/Src/uart_protocol.c` 完全一致）

```
$<CMD>[,<ARG>...]*<CK><CR><LF>
CK = '$' 与 '*' 之间所有字节逐字节 XOR，2 位大写十六进制
```

| 帧 | 含义 | 固件回 |
|---|---|---|
| `$CAR,FWD,800*3D\r\n` | 前进 **800 毫秒**后自动停（文档 A 项验收判据） | `$OK*04\r\n` |
| `$CAR,FWD,800,900*28\r\n` | 前进 800ms，速度 PWM=900（可选第二参数） | `$OK*04\r\n` |
| `$CAR,STOP*64\r\n` | 立即停车 | `$OK*04\r\n` |
| `$CAR,BWD,300*32\r\n` | 后退 300ms | `$OK*04\r\n` |
| `$CAR,SPINL,500*2D\r\n` / `SPINR` | 原地左 / 右转 | `$OK*04\r\n` |
| `$CAR,TURNL,...` / `TURNR` | 前进中左 / 右转 | `$OK*04\r\n` |
| `$CAR,SPD,850*2A\r\n` | 设默认速度档（PWM 0~999） | `$OK*04\r\n` |
| `$CAR,MODE,1*62\r\n` | 切模式：0 遥控 / 1 避障 / 2 循迹 | `$OK*04\r\n` |
| `$PING*10\r\n` | 探活（两个节点都认） | `$OK,PONG*3E\r\n` |

错误码沿用机械臂那套：`1` 帧/校验错、`2` 未知命令、`3` 参数错、`4` 状态禁止。

🔴 **800 是「毫秒」，不是厘米**。底盘没有编码器 / IMU / 里程计，是**纯开环定时**，
「走 X cm」只能靠时间估（实测误差 20~40%）。这是硬件缺口，不是代码问题，别写进简历当成闭环。

**本地仲裁（安全）**：固件侧硬闸门 `时长 ≤ 5000ms`、`PWM ≤ 999`、`MODE ≤ 2`，
超量程直接 `$ERR,3*5A\r\n`，车不会动。对应架构原则「LLM 只能提议，本地仲裁器才授权」。

**向后兼容**：老的手机蓝牙单字符协议（`F/B/L/R/S/1~6`）**一个没删**。
主循环靠「见到 `$` 就进帧模式、见到 `\n` 退出」把两条协议分开，
所以帧里的 `F`（`$CAR,FWD...`）不会被误当成「前进」。另有 200ms 帧间超时防半帧卡死。

1. 发 `$PING*10\r\n` → 回 `$OK,PONG*3E\r\n`；

## 六、README 三行法（面试前复习提纲）

**模块 A：`car/car_frame.c`（统一帧协议层）**

- **① 用了什么语法**：`static` 私有变量做封装、`enum` 给动作起名、`struct` 打包一条命令、
  **函数指针**（`car_on_command_fn` / `car_send_fn`）做回调注册、四态 `switch` 状态机收字节、
  自己写 `parse_u32()` 而不用 `atoi`、`strncmp` 逐字段匹配。
- **② 为什么这么设计**：协议层**不 include `stm32f4xx.h`**，硬件动作通过回调注入 ——
  这样在 PC 上用 gcc 就能编译测试，不用接板子；而且机械臂 `uart_protocol.c` 用的也是
  `$...*CK` 这套语法，两个节点共用一种帧格式才叫「统一帧」。手写 `parse_u32` 是因为
  `atoi/sscanf` 在单片机上会拖进一大块库，碰到非法字符行为也不好预测。
- **③ 不这么写会出什么问题**：把 `BT_SendStr` / `Car_Forward` 直接写进协议层 ⇒ 没法在电脑上测，
  每次改协议都要烧板子；用 `atoi` ⇒ 上位机发个 `FWD,abc` 会得到 0、车莫名不动；
  不给定长缓冲上限 ⇒ 串口灌垃圾字节就把数组写爆，裸机没有 OS 保护，直接跑飞。

**模块 B：`car/main.c`（双协议主循环 + 非阻塞定时停）**

- **① 用了什么语法**：`s_in_frame` 标志位区分「帧模式 / 单字符模式」；`millis()`
  记时间戳做定时；`car_frame_init()` 注册两个回调；原来的单字符 `switch` 整段包成
  `Legacy_OneChar()` 保留。
- **② 为什么这么设计**：`$CAR,FWD,800*3D` 里那个 `F` 如果也走老协议，车会在解析帧的
  过程中被莫名其妙启动；用「见到 `$` 才进帧模式」就把两条流分开了。定时停用
  `millis()` 比 `delay_ms(800)` 好：后者把 CPU 死等 800ms，期间上位机喊 `STOP` 根本收不到。
- **③ 不这么写会出什么问题**：不区分模式 ⇒ 帧里每个字母都可能触发一次老命令；
  用阻塞延时 ⇒ 急停失效、自动模式（避障/循迹）卡住 800ms；不留单字符协议 ⇒
  已经调通的手机蓝牙演示当场作废。

**模块 C：`kunpeng/car/car_gateway.py`（鲲鹏侧发帧网关）**

- **① 用了什么语法**：`argparse` 的 `add_mutually_exclusive_group` 让 `--port/--tcp/--dry-run`
  三选一；`with` 语句自动关串口/TCP；`socket` / `pyserial` 可选导入；`%02X` 格式化校验和；
  把「发帧 + 收回包」抽成 `_read_reply()` 配一个 `reader` 回调。
- **② 为什么这么设计**：**独立进程**，不碰已经实机验收的 `web_control.py` —— 改那个
  Flask 要重启、有回归风险。网关只依赖标准库，没装 `pyserial` 也能用 `--dry-run` 先验
  校验和，符合「先做不依赖 ESP32 硬件的一段」这条落地顺序。将来要挂 `/api/car`，
  `import build_frame()` 一行就够。
- **③ 不这么写会出什么问题**：把底盘帧塞进 Flask ⇒ 一次误改把机械臂网页控制台也带崩；
  校验和靠手算 ⇒ `$PING*10` 能对、`$CAR,FWD,800` 大概率算错，排障时会误判成串口不通。
