### 第 1 条 · 板上 `opencv 5.0.0` 缺 `cv2.calibrateHandEye`，`solve` 必失败

**现象**
板上诊断回执 `CV2 5.0.0` / `HAND_EYE False` / `DISPLAY NONE`。旧版 `cmd_solve` L315-320 一进来就打印
「请安装 4.x 版：`pip install 'opencv-python-headless==4.10.0.84'`」然后 `return 1`；也就是说按原样跑，
内参和样本全采完，最后一步解算直接失败，白摆十几张棋盘格。

**排查过程**
1. 读 `handeye_calib.py` L312-349，确认 `cmd_solve` 只读 `samples.json`（`R/t_gripper2base`、`R/t_target2cam`），
   输入输出全是 numpy array，唯一外部依赖就是 `cv2.calibrateHandEye(..., CALIB_HAND_EYE_TSAI)`。
2. 查 OpenCV 模块归属：`calibrateHandEye` / `CALIB_HAND_EYE_TSAI` 属于 **opencv-contrib** 扩展，
   主包（`opencv-python`，含 `opencv-python-headless`）通常不带 ⇒ 代码里自带的装包建议**本身很可能就是错的**，照装仍缺。
3. 再看板上环境：`cv2 5.0.0` / `numpy 2.0.2` 是已实证 S3b 视觉链路（`detector_service.py` / `stage1_yolov8.py`）
   的依赖。为一次标定 `pip` 降级到 4.x，会覆盖它、并可能撞 numpy 2.x 的 ABI ⇒ 牵一发动全身。
4. 结论：不动环境，只动自己那一个文件的求解实现。

**根因**
① 代码依赖了一个不在主包里的 contrib API；② 代码内置的降级提示写错了包名；③ 更本质的取舍是
「为一个函数去动一条已跑通的链路」不划算——问题在**耦合**，不在版本。

**解决**
把 `cmd_solve` 改成纯 numpy 两步：
- 旋转：由 `A·X = X·B` 得 `R_A R_X = R_X R_B`，用 `vec(AXB)=(B^T⊗A)vec(X)` 拉平成
  `[I⊗R_A − R_B^T⊗I]·vec(R_X)=0`，堆所有两两姿态对后 `np.linalg.svd(..., full_matrices=False)`
  取最小奇异值的右奇异向量，reshape 回 3×3 再做 Procrustes 投影到 SO(3)。
- 平移：`(R_A − I)t_X = R_X t_B − t_A`，`np.linalg.lstsq` 最小二乘。
- SVD 零空间符号任意，用「平移方程残差」在 `+v/-v` 两个候选里挑小的那个。
- 用 `selftest` 合成数据自证：埋一个已知 X，反解 `T_t2c`，再求解比对。实测
  `‖R_est−R_true‖=5.85e-16`、`‖t_est−t_true‖=2.47e-16`，还原出的 `[4.50,-3.00,8.50]cm`
  与真值 `[0.045,-0.030,0.085]m` 完全一致。
- 顺手修掉 `full_matrices=True` 隐患：20 组样本时 `K` 有 1710 行，默认会开 1710² 的左奇异矩阵，
  板上内存没必要；`full_matrices=False` 只留 9×9 的 Vt，结果一样。

**一句话面试说辞**
「板上的 opencv 缺一个 contrib 里的手眼标定函数，我没有去降级整条视觉链路，而是把 AX=XB 用
`vec + Kronecker 积 + SVD 零空间` 自己用 numpy 解出来，再用合成数据把已知变换埋进去反解验证，
恢复到机器精度 `1e-15`，这样零装包、零环境改动、还能自检自证。」

### 第 2 条 · `DISPLAY NONE` 下 `cv2.imshow` 崩；去掉按键后差点引入死循环

**现象**
板上 `DISPLAY NONE`（openEuler 服务器版无桌面）。旧版 `cmd_intrinsics` L216 / `cmd_collect` L272
用 `cv2.imshow` + `cv2.waitKey` 做「按 c 存、按 q 结束」，无 X11 时一调用就崩。
改成「定时自动采集」后自查又发现：`while saved < count` 只剩「采满」一个出口，
若棋盘格一直没进视野，循环**永不退出**，会把板子卡死。

**排查过程**
1. 逐个核对 cv2 API 对 DISPLAY 的依赖：只有 `imshow` / `waitKey` / `destroyAllWindows` 需要窗口系统；
   `VideoCapture` / `imwrite` / `findChessboardCorners` / `drawChessboardCorners` / `solvePnP` /
   `calibrateCamera` 都是纯计算或纯文件 IO，无头可用。
2. 走查新循环的退出条件：原版靠「按 q」，新版把键盘交互删了却没补兜底 ⇒ 单一出口失效即死循环。
3. 用 mock 注入合成棋盘格帧跑真实循环验证：把 `imshow/waitKey/destroyAllWindows` 换成「一调用就抛异常」，
   确认无头模式全程没碰 GUI。

**根因**
不是 opencv 的问题，是**交互模型换了但生命周期没跟着换**：从「人按键驱动」变成「定时器驱动」后，
必须补一个与采集成功无关的独立退出条件。

**解决**
- `_is_headless()` 自动检测 `DISPLAY`（空即无头），另留 `--headless` 显式开关；所有 GUI 调用收进 `if not headless`。
- 采集改为 `--count` 张 / `--interval` 秒定时自动存，可选 `--save-dir` 把帧存成 jpg 事后复核。
- 新增 `--timeout`（默认 300 秒）作为独立出口，超时打印「已存 x/N，退出」并返回非 0。
- 冒烟验证两例：正常帧 → 采满 5 张、`rc=0`、写出文件、GUI 零调用；
  mock 成「永远检测不到棋盘格」→ 0.3 秒超时退出、`rc=1`，不死循环。

**一句话面试说辞**
「无桌面环境下我先把 cv2 里真正依赖 X11 的三个函数隔离出来，改成定时自动采集；随后发现自己删掉
『按 q 退出』后循环没了兜底，就补了独立超时出口，并用 mock 相机帧把『采满』和『超时』两条路径都跑了一遍。」

### 第 3 条 · PC 命令环境误判：在 PowerShell 里用了 Git Bash 语法

**现象**
给小Z 的 scp 命令写成 `cd /d/*/STM32*/4.*/... && scp ...`，他在 `PS D:\...>`（PowerShell 5.1）里执行，
报 `标记"&&"不是此版本中的有效语句分隔符`（`ParserError / InvalidEndOfLine`）。

**排查过程**
看回执提示符是 `PS D:\...>`，不是 Git Bash；对照项目里早就记录过的两条环境事实：
PowerShell 5.1 不支持 `&&` / `||`，且 PowerShell 不认 `/d/...` 这类 Git Bash 挂载路径。

**根因**
把历史上给 Git Bash 用的「ASCII 通配符绕开中文路径」技巧，套到了一个实际是 PowerShell 的会话上；
命令标注的执行位置与实际执行环境不一致，属于助手给命令前没核对环境。

**解决**
撤回该命令，改成 PowerShell 语法：
`Set-Location "D:\简历\STM32项目\4.ESP32-S3项目\RoboticArm_Kunpeng\kunpeng\robot"; scp handeye_calib.py arm_host.py root@10.160.120.1:~/kunpeng_vision/`
（`;` 分隔、Windows 绝对路径、scp 只传纯文件名）。并把「按提示符定命令语法」写进项目长期记忆。

**一句话面试说辞**
「给可复制命令时我会先看终端提示符定语法——PowerShell 5.1 没有 `&&`、也不认 `/d/`，
这次先撤回错误命令再给 `Set-Location` + `;` 的版本，避免让用户照着跑不通的命令空转。」

### 第 4 条 · `collect` 只读 STATE 不下发，且 `/api/state` 返回「未连接」

**现象**
核准批 2 命令时只读走查代码，发现三个会让真机实标白跑的事实：
① `cmd_collect` 全程只有 `host.state()` / `host.parse_state()`，**没有任何 JOINT/MOVE 下发**；
   STATE 返回的是固件内部记录的脉宽目标值（10:17 实测＝初始位），手动掰臂不改变它。
   停掉 `web_control.py`(5000) 后没有任何下发通道 ⇒ 12 个姿态摆不出来、`samples<3` ⇒ `solve` return 1。
② 若**不停** 5000 而让 collect 直连 `serial.Serial("/dev/ttyUSB0")`，两个进程的 `_rx_loop` / `_read_frame`
   会同时 `read()` 同一个字符设备，抢走彼此的 `$OK,S,...` 帧 ⇒ 每组 STATE 解析失败被跳过，同样白跑。
③ 板上运行态诊断回执：`/api/state` 返回 `{"error":"未连接","ok":false}` —— 5000 虽带 `/dev/ttyUSB0`
   参数在跑，但控制链路根本没连串口，滑杆 / JOINT / STATE 全不通。

**排查过程**
1. 读 `handeye_calib.py` 的 `cmd_collect`，确认只有 `state()` 读、没有 `joint()`/`move()` 写。
2. 读 `web_control.py` 的 `api_state()`（L1492）：`_HOST is None` 直接返「未连接」；`resp = _HOST.cmd("STATE")`
   由 web_control 独占串口完成，返回 `{"ok":true,"pulses":[6路]}` ⇒ 说明「让 web_control 一个人读串口、
   collect 走 HTTP 拿结果」可行，且不抢帧。
3. 读 `main()` 的 serial 分支（L1720-1725）：只把 `args.serial` 存进 `_HOST_STATE["port"]`，**不创建 `_HOST`**
   ⇒ 解释了「未连接」的根因，也确认 `POST /api/open` 可零重启恢复（不必重启 5000）。
4. 用 mock HTTP + 合成棋盘格帧跑 `cmd_collect`：正常帧采满 5 组、`serial` 全程未 import；
   `ok=false` 时每组跳过会一直刷屏到 `--timeout`(300s) ⇒ 补进循环前预检，立刻 `return 1`。

**根因**
不是环境没配好，是**「谁负责读串口」这一职责没定清楚**：标定程序把自己当成了串口主人，
但真正能改变臂姿态（下发 JOINT）的是 `web_control.py`。两个读者 + 一个只写的控制通道，
必然竞争消费字节流；再加上 5000 重启后没重新 `/api/open`，控制通道本身是断的。

**解决**
- `cmd_collect` 去掉 `import serial` / `ArmHost`，新增纯标准库 `_read_state_pulses()`：
  `POST /api/state` 读 6 路脉宽，`--state-url` 可配（默认 `http://127.0.0.1:5000/api/state`）。
  `web_control.py` **全程不动**，只由它独占串口；用户在网页滑杆摆臂，collect 走 HTTP 取结果。
- 进采集循环前先探一次状态源：未连串口（`ok=false`）时打印「请先 POST /api/open 连串口」并 `return 1`，
  不写空文件、不刷屏到超时。运行中偶发失败仍只跳过该组。
- 概念（大白话）：不抢话筒，改问主持人要答案；规范定义：单一资源独占 + HTTP 代理读取，
  避免对同一字符设备的并发 `read()` 竞争消费。
- 相机侧另需先停 `detector_service.py`(8080) 释放 `/dev/video0`（它 `--source 0` 一直占着）。

**一句话面试说辞**
「我发现标定程序和 Web 后台抢同一个串口：两个进程各自 `read()` 会把一帧数据拆给两个人。
我没有去加文件锁，而是让唯一有控制权的 Web 后台独占串口，标定程序改成 HTTP 问它要 6 路脉宽；
还顺手发现后台重启后没重新连串口，加了进循环前的预检，未连接就立刻报错，不让人白等五分钟。」

### 第 5 条 · 占位标定数据把目标点推到臂展之外，13 项端到端检查一次全挂

**现象**
「软件先行」阶段写好 `handeye_geometry.py`（X 的消费者）+ mock 验证脚本，本机跑 `test_eye_in_hand_mock.py`：
45 项检查里 **13 项 FAIL**，全部集中在「试算」之后的环节，报错统一是
`逆解失败：目标点超出机械臂可达范围 (d=25.7, L1+L2=25.2)`。
奇怪的是：几何模块自己的 `selftest` 9 项全绿、旧接口 `/api/ik/solve` 回归也全过 —— 说明**数学没错，是喂进去的数不对**。

**排查过程**
1. 看报错里的两个数：`d=25.7`、`L1+L2=25.2`。臂展上限来自 `arm_params.json`（10.6+14.6），是硬的；
   `d=25.7` 是手眼链算出的桌面点到基座的水平距离 ⇒ 越界 0.5cm，非常"贴边"，不像随机错。
2. 单独跑 `handeye_geometry.py` 诊断：画面中心像素 `(320,240)` → `x=-3.21, y=21.60`，`d=21.84` **在范围内**。
   同一份代码、不同命令结论相反 ⇒ 差异在**输入**，不在算法。
3. 对比两次输入：诊断用的是 `handeye_X.json` 里的占位 X（x 偏 1.5cm）；
   mock 测试里 `[5]` 走的也是它 —— 但 `[5]` 之前我先改了占位偏移…… 回溯 `gen_placeholder_calib.py`，
   当前占位 X 的平移是 `[0.015, 0, 0.030]`（x 偏 1.5cm）。
4. 把相机位置打印出来交叉验证：初始位 `[1580,1900,2400,700,1450,1500]` 下，
   末端 FK 出来约在 `(0, 16.9, 7.3)`cm，相机动 1.5cm 后光轴朝下的落点正好被推到 25.7cm。
   **占位值本身"合法"（矩阵正交、行列式=1、焦距为正），但不代表它落在工作空间里。**
5. 又试了 5 组姿态量化边界：`d` 分别 21.8 / 24.1 / 19.6 / 26.3 / 18.3cm ⇒ 证实"越界与否"完全由姿态 + 相机偏移共同决定。

**根因**
把"占位"误解成了"随便填个合法矩阵就行"。实际上占位数据虽然不追求精度，
但**必须落在真实机械臂的可达工作空间内**，否则下游 IK 一定拒绝，链路等于没通。
更深一层：相机装在末端，它"看得见"的桌面区域和"臂够得着"的区域本来就只是部分重叠 ——
占位相机又额外前移 1.5cm，把重叠区域进一步推出边界。

**解决**
- 占位 X 的平移改为 `[0, +2cm, +3cm]`（沿臂前向微移、向上抬 3cm），初始位下 `d` 从 25.7 降到 **21.84cm**，留 3.4cm 余量；
  在 `gen_placeholder_calib.py` 里写清楚"为什么是这个值"，并记录第一版踩坑数据。
- mock 测试的"换姿态"用例改用 `[1450,1850,2350,730,1480,1500]`（`d=24.14cm`），不再用越界姿态。
- **修正一条测试判据（重要）**：把"换姿态后 IK 必须成功"改成"换姿态后必须仍返回工作台坐标，IK 可单独失败"。
  理由是「相机看得见」≠「臂够得着」，后者是真实物理约束，不该被测试当成 bug。
- 45 项复跑全绿。顺带补上 `collect` 的 `--square` 尺度防呆（内参文件记 `square_m`，`collect` 自动继承并在不一致时告警）。

**一句话面试说辞**
「我先在没有硬件的情况下用合成数据把视觉定位链跑通了，结果 13 项挂掉，报错是目标点超出臂展。
我没有去改 IK 的参数让它'算得过去'，而是往回查输入：占位的手眼矩阵虽然数学上合法，
但把相机前移 1.5cm 后，光轴落点被推出了 25.2cm 的臂展边界。
这让我认清一件事 —— 占位数据也得按真实工作空间设计，而'相机看得见'和'机械臂够得着'是两回事，
我把测试判据也改成了分别验证这两点。」

### 第 6 条 · `solve` 报「旋转激励不足」，实际是方程根本没有解

**现象**

实机采完 12 组（`max_pair 37.9°`）后 `solve` 输出：

```
AX=XB 姿态对 66 组；奇异值最小/次小 = 1.844e+00 / 2.002e+00
⚠️ 旋转激励不足（姿态间相对旋转太小或转轴太单一），X 可能不可靠
选定候选解：平移方程残差 = 9.586e-01
平移 t = [-40.24, -1.98, -16.02] cm
欧拉角 rpy = [126.0, 17.5, -144.2] 度
```

**排查过程**

1. 先跟合成自检对照：合成数据（一定有解）`σ_min = 1.9e-15`、`残差 = 1.5e-15`。
   实机两个数差了 **15 个数量级** —— 这不可能是「精度差一点」。
2. 再看姿态覆盖：`max_pair 37.9°`，比上一轮的 17° 翻倍，说明**不是「动得太少」**。
3. 用一个不依赖未知数 X 的判据体检数据：`R_B = R_X^T·R_A·R_X` 是相似变换，
   **旋转角度是相似变换的不变量**，所以 `angle(R_A)` 必须等于 `angle(R_B)`。
   逐对算 `|angA − angB|`，就能看出哪些样本自相矛盾。
4. `t` 模长 42.9 cm —— 相机装在 J4 轴上，物理上只能 5~10 cm，直接判死。

**根因**

代码只有一个判据「`σ_min/σ_2nd > 1e-3` 就警告激励不足」，它分不清两种情况：

- 激励不足（零空间 ≥ 2 维）：**仍然有精确解**，最小二乘残差接近 0；
- 无解（零空间 0 维）：**没有任何答案能同时满足**，残差显著为正。

实机是后者（`resid = 0.96 m`），却被报成前者。两者修法完全相反 —— 前者要多摆姿态，
后者要查「数据为什么自相矛盾」（J4 重力下垂 / 标定板被碰动 / `arm_params.json` 映射不符）。
按错误提示去做，会白采好几轮。

**解决**

改成三级分类，判定顺序不能交换：

```
① 残差 > 2 cm       → NO_SOLUTION（量级差太远，只能是数据矛盾）
② 否则 ratio > 1e-3 → WEAK_EXCITATION
③ 否则残差 > 1 mm   → NO_SOLUTION（零空间唯一却拟合不上，同样是矛盾）
④ 其余              → OK
```

阈值不是拍的，是四组实测数据反推的：

| 数据 | ratio | resid | 判定 |
|---|---|---|---|
| 合成正常 | 5e-16 | 1.5e-15 m | OK |
| 单轴小角度 | 7.3e-1 | 3.4e-3 m | WEAK |
| 人为破坏 1/3 样本 | 5e-16 | 2.1e-1 m | NO_SOLUTION |
| 实机 | 9.2e-1 | 9.6e-1 m | NO_SOLUTION |

关键点：**单轴退化的 ratio 也很大**（0.73），只能靠残差量级（毫米 vs 十几厘米）把两者分开。

同时改了写盘策略：无效解写 `handeye_X.rejected.json`，**不动 `handeye_X.json`**。
因为 `web_control.py --eye-in-hand` 默认加载后者，而那个矩阵本身是正交的、能通过全部合法性检查，
只会让点选坐标悄悄偏十几厘米 —— 静默错误比报错危险得多。

**一句话面试说辞**

「实机标定时 solve 报了『激励不足』，但对照合成数据发现两个指标差了 15 个数量级，
说明不是精度问题而是方程无解。我加了一条不依赖未知数的判据 —— 旋转角是相似变换的不变量，
逐对比对机械臂转角和相机观测转角，定位出样本自相矛盾。然后把单判据改成三级分类，
并且让无效解写进 `.rejected.json` 而不是正式文件，避免下游静默加载一个错误的矩阵。」

### 第 7 条 · `PING` 也返回空串：USB 瞬时掉线后读线程静默死亡

**现象**

10:43 三条全绿（`open` / `PING` / `state` 六路脉宽都对），摆臂约 3 分钟后：

```
{"ok":true,"resp":""}          ← PING
{"ok":true,"resp":""}          ← STATE 原始应答
{"ok":true,"pulses":[]}        ← /api/state
```

`collect` 进循环前的预检拦住并秒退（「状态源不可用」），没有白跑 900 秒，也没写空 `samples.json`。

**排查过程**

1. `PING` 是最轻的命令，臂静止时毫秒级返回；`PING` 都空 ⇒ **一个字节都没回到**，
   排除「STATE 排队超时」。
2. 核 `api_open()`：L1491-1496 确实先 `close()` 再重建，不存在 fd 泄漏（这条猜想被撤回）。
3. 关键证据：`ls -l /dev/ttyUSB*` 显示节点 mtime 是 **10:56** —— 而 `ls` 本身不会改节点时间，
   说明它在 10:56 被**重新创建**过。`dmesg` 里没有 `disconnect`，是因为 ring buffer 被
   `[bbox]` 的 LPM 转储刷掉了。
4. 读源码确认机理：`_rx_loop()` 是 `except Exception: break` —— 读异常时线程直接退出，且不重连。

**根因**

USB 瞬时掉线（摆臂振动 + 舵机电流冲击）→ 内核删除旧节点、重新枚举 → `SerialHost.ser`
的文件描述符仍指向**已删除的旧节点**。pyserial 不感知节点被删，`is_open` 仍返回 True，
`write()` 也不报错 → 数据写进废弃的 fd → `rxq` 永远空 → `send()` 超时返回 `""`
→ `api_state()` 把空串切成空列表，返回 `ok:true, pulses:[]`。
**整条链路没有任何一处报错**，上层只能看到「设备在线但没数据」。

掉线的物理原因也查清了：相机（`0bda:1376`）与 CH341（`1a86:7523`）原来挂在同一个
hub（`usb 7-1`）下，而扩展坞**不增加供电**（只做协议分发，总电流仍受上行端口约束）。
舵机瞬间电流一大，hub 整体复位，相机和串口一起掉。改成 **CH341 直连板子、相机走扩展坞**后，
12/12 组全部采到。

**解决**

给 `SerialHost` 加 `_dead_reason` 状态位，三处集中拦截：

- `_rx_loop` 的 `except`：只在**非主动关闭**时记录原因（`close()` 会先置 `_reader_alive=False`，
  那时 `ser` 可能已是 `None`，不该记成断开）；
- `_write()`：链路已死直接抛 `RuntimeError`，不再往废弃 fd 灌数据；
- `send()` 等待循环：每轮检查一次，读到死立刻抛，**不必等满 timeout**
  （实测 0.05 s 就报错，而不是 1.0 s 后返回空串）。

验证 11 项全过，其中一项专门确认「健康但无应答仍返回空串」—— 加守卫不能把正常无应答误报成断线。

**一句话面试说辞**

「串口偶尔返回空数据，一开始怀疑固件没应答。后来用设备节点的 mtime 证明 USB 曾经重新枚举过，
而 pyserial 对已删除的节点仍认为 `is_open`、`write` 也不报错，数据全进废弃描述符。
我加了链路死亡标记，在读线程异常、写入、等待三个点显式报错，把静默失败变成明确故障。
物理侧定位到扩展坞不增加供电、相机和串口共用 hub，改成一拖一后就不再掉线。」

### 第 8 条 · 好数据也会被判「无解」：残差定义错 + 棋盘格边长当成了已知量

**现象**

① 实机 `probe`（1 组，`--square 0.0080`）输出 `标定板距相机 0.19 m`、`|t| = 0.192 m`。
按腕点几何（腕高 18.7 cm、光轴俯角 49°）应得 `≈0.248 m`，**差 23%**，
差点让我判定「尺子还是量错了」，或者反过来判定「模型错了」。

② 同时发现一个更隐蔽的坑：把 12 组合成数据加上 2 mm 定位噪声再 `solve`，
会被判成 `NO_SOLUTION`（`resid = 3.2e-2 m`）—— **好数据被门限自己枪毙了**。

**排查过程**

1. 先查 23% 的差是不是尺度：把「相机到标定板的距离」写成腕点几何 + 相机沿工具轴前移 δ 的函数，
   解 `|t| = 19.2 cm` 得 δ ≈ 5.6 cm。**相机真的装在 J4 支架上前伸了几厘米**（镜头不在 J4 轴心上）。
   ⇒ 一旦相机有前伸量，`|t|` 就必然小于按腕点算的距离，**「用距离反推 `--square`」这条判据根本不成立**。
2. 再查 ② 的残差：`resid` 是 `‖A·t − b‖`，即 **全部方程堆在一起的总范数**。
   12 组样本有 66 个姿态对、198 行方程，每行 2~3 mm 噪声，总范数就是 `√198 × 2.5mm ≈ 3.5cm`；
   3 组样本只有 3 个对、9 行，同样的噪声只有 `√9 × 2.5mm ≈ 7mm`。
   ⇒ **同一个物理精度，样本越多「残差」越大**，拿它跟固定门限比等于自欺欺人。

**根因**

两条，都是「把未知量当成了已知量、把错的量纲塞进了门限」：

- `--square` 是用尺子量屏幕得来的，差 20%~30% 很正常，却被当成已知常量。
  尺度错不会让方程无解，只会让**相机侧平移整体等比放大**（FK 侧是真的），于是残差涨到厘米级、
  被三分类判成 `NO_SOLUTION`，然后人去查根本不存在的「J4 下垂 / 标定板被碰动」。
- 残差门限 `1 mm` 是拿合成数据（机器精度 `1e-15`）定的，**是数值噪声门限，不是硬件门限**。
  实机的角度映射误差、连杆长度实测误差、内参误差，任何一项都在毫米级。

**解决**

1. `solve` 把尺度当未知量一起解：`[ (R_A − I) , −R_X·t_B ]·[t_X; s] = −t_A`，
   3n 行 4 列最小二乘；求得 `s` 后把相机侧平移整体乘回去再重解 `t_X`。
   终端多打一行 `尺度自校正：s = 1.2875 ⇒ 数据隐含方格边长 0.0103 m（采集时填 0.0080 m）`，
   `s≈1` 说明尺子量准了。**无效解时不提示改 `--square`**，因为那时的 `s` 也在拟合噪声。
2. 残差改成**每行 RMS**（`总范数 ÷ √行数`），单位仍是米、含义变成「平均每条方程差几毫米」，
   与样本数无关，才能和 1 cm / 2 cm 的物理门限直接比。
3. 门限 `RESID_SOFT` 从 `1 mm` 改成 `1 cm`（实机可接受边界），`RESID_HARD` 保持 `2 cm`。
4. 合成数据回归（PC，`numpy 2.5.2`）：

| 数据 | `status` | 恢复的 `s` | 隐含方格 | 真值 |
|---|---|---|---|---|
| 尺度正确 | OK | 1.0000 | 0.0080 | 0.0080 |
| 尺度偏小 29% | OK | 1.2875 | 0.0103 | 0.0103 |
| 尺度偏大 3.1 倍 | OK | 0.3200 | 0.0026 | 0.0026 |
| 尺度正确 + 2 mm 噪声 | OK | 0.9936 | 0.0079 | 0.0080 |
| 单轴退化（激励不足） | WEAK_EXCITATION | 1.0000 | 0.0080 | 0.0080 |

`solve` 的 5 组 `selftest` 与「破坏样本必须判无效」全部仍通过。

**一句话面试说辞**

「手眼标定连着两轮报无解，我先怀疑几何不可观。后来发现两个都是自己挖的坑：
一是棋盘格边长我拿尺子量屏幕，差三倍就等比放大相机侧平移，FK 侧没动，方程自然矛盾；
二是残差我用了全部方程的总范数，它随样本数按 √n 涨，样本一多就把好数据判死了。
改法是把尺度当成未知量和 X 一起最小二乘解出来，残差改成每行 RMS，
现在程序会直接打印『数据隐含的方格边长』——尺子误差和真故障一眼就分开了。」

### 第 9 条 · 判据反了：好数据被判「激励不足」，退化成一条线的数据却被判 OK

**现象**

准备第三轮实采前，为了确认「J1 只能扫 ±10° 够不够」，用真实 FK 正演一组合成数据（12 组、加 0.2°/1mm 噪声）
再反解，结果自相矛盾：

| 数据 | `ratio` | 解出来的 `|t|` 误差 | 三分类判定 |
|---|---|---|---|---|
| 两轴姿态 + 0.2° 噪声（**可用**） | `2.0e-2` | **3 mm** | ❌ `WEAK_EXCITATION` |
| 只动 J1、只转一根轴（**不可用**） | `3e-17` | 45 cm | ✅ `OK` |

也就是说：能用的解被拦、垃圾解放行。判据反了。

**排查过程**

1. `ratio = σ_min/σ_2nd` 来自旋转方程的 9×9 系数矩阵。`σ_min` 是「零空间方向有多松」，
   理论上无噪声时恒为 0；**实机一旦有噪声，`σ_min` 就不再是 0，它的大小等于噪声本身**。
   于是 `ratio` 实际测的是「噪声小不小」，而不是「几何摆得好不好」——门限写 `1e-3`，
   等于要求噪声比几何量化误差还小 1000 倍，实机永远做不到。
2. 反方向更致命：所有姿态只绕同一根轴转时，解族是 SO(3) 里的一条曲线，**曲线每一点的切向都是那个零空间向量**，
   所以 9×9 的零空间依旧是「一维」，`ratio` 依旧是 `1e-17`，完全看不出退化。
   两个测试分别在噪声和退化两头踩空，说明这个指标从定义上就不对。
3. 换指标：`[R_A − I]` 的**秩**。每个 `(R_A − I)` 都看不见自己那根转轴，
   所有姿态绕同一根轴 ⇒ 堆起来的矩阵秩 2，`σ_min = 0`；两根轴不平行 ⇒ 秩 3，`σ_min` 明显大于 0。
   实测（真实 FK + 独立噪声，各 8~15 次取中位）：

| 姿态集 | `axis_cond = σ_min/σ_max` |
|---|---|
| 两轴：J1 ±10° × J4 俯仰 32~50 | **0.70**（0.3°~2° 噪声几乎不变） |
| 两轴：J1 ±8° × J4 俯仰 32~50 | 0.63 |
| 只动 J1（±10°） | 0.028（0.3° 噪声）→ 0.19（2° 噪声） |
| 只动 J4（俯仰 30~50） | 0.023 → 0.16 |

**根因**

用「奇异值比值」当激励判据，是把**噪声指标**当成了**几何指标**。
`ratio` 的分子会被噪声顶起来，分母只跟转轴多样性有关，两者混在一个数里，
既分不开「数据干净」和「几何好」，也分不开「数据脏」和「几何差」。

**解决**

1. `solve_handeye_axxb()` 新增 `axis_cond = σ_min/σ_max of [R_A−I]`，写进 `diagnostics` 并打印；
   `classify_handeye_solution()` 的判据改成 `axis_cond < 0.25` → `WEAK_EXCITATION`
   （比「好姿态」低 2.8 倍，比「退化姿态」高一个数量级）。
2. `RATIO_WEAK` 从 `1e-3` 放宽到 `0.3`，只作为第二道辅助（它仍能抓住「同一根轴但角度差异极大」的怪数据）。
3. `|t|` 增加**下限** 2 cm：相机不可能贴在夹爪尖上，小于它基本是解跑飞，直接判无解。
4. `selftest` 加第 6 组「单轴退化样本必须判 WEAK」——这条自检锁住阈值，
   否则以后调阈值时又会让一个 45 cm 的垃圾 X 悄悄写进 `handeye_X.json`。
5. 顺带用同一套正演确认了**J1 只能扫 ±10° 也够用**：|t| 误差 3~6 mm、旋转误差 0.4~0.6°，
   两轴张成度 0.70。所以不需要为了激励去硬撑 ±18°（那会让棋盘出画，见第 10 条）。

**一句话面试说辞**

「我原来用『旋转方程奇异值比值』判断激励够不够，后来用真实正演一测，发现这个指标两头都不准：
有噪声时好数据被判激励不足，只绕一根轴转的坏数据反而判 OK。原因是它的分子在实机上等于噪声，
而单轴退化时解族是一条曲线，零空间维数还是一维，比值看不出来。改成看 `[R_A−I]` 的秩——
单轴退化时它必然掉到 0，两轴不平行时才明显大于 0——阈值就好定了，还加了自检锁住它。」

### 第 10 条 · 姿态公式镜像：位置说"往下俯"，姿态说"往上仰"

**现象**

2026-11-10 20:22 第三次实采 12 组（±6° 扫幅、棋盘居中对齐、距离 0.19~0.22m），`solve` 仍然判无解：

```
AX=XB 姿态对 66 组；奇异值最小/次小 = 1.636e-01 / 9.754e-01（比值 1.68e-01）
转轴判据：σ([R_A−I]) 最小/最大 5.19e-01（需 ≥ 0.25）   ← 激励完全够
尺度自校正：s = 0.7461；残差 RMS 1.727e-02 → 1.667e-02 m
平移 t = [-8.36, -0.66, -10.24] cm（模长 13.2 cm）
三分类：❌ 无解
```

三条自相矛盾的读数：**激励够（0.52）、零空间一维（姿态"看着对"）、平移却差 16.7mm**。
另外 `diagnose_he.py` 第 6 段给出决定性证据：标定板在基座系的位置 P
**极差 4.65 / 10.52 / 5.06 cm**，而且 `ty` 随 J4 单调变化（−0.448 cm/°），`tx` 随 J1 单调变化。

**排查过程**

1. 先排除"棋盘被碰动"：`dP` 的 `ty` 分量随 J4 **周期性**变化（32°/41°/50° 三档各一组值），
   而时间顺序是 J1 单调、J4 循环。**随时间漂移不会呈现"按 J4 分三档"的形状** ⇒ 是姿态相关误差，不是棋盘滑了。
2. 再排除"连杆尺寸错"：本机做参数扫描（L1/L2/L3/H 各 ±5%、J4 轴位置 ±2cm、J1 轴偏心 ±2cm），
   发现**全部被 X 吸收，残差恒为 0.00mm**。原因：这 12 组里 J2/J3/J5/J6 全程不动，
   `FK_true = FK_nom·E`（E 为末端系常量）⇒ X 天生能吸收，所以"改尺寸"这条路根本走不通。
   能被残余误差暴露的只有一类：**姿态随关节角变化的方式不对**（R_fk(q) ≠ R_true(q)·常量）。
3. 于是逐行核对 `fk_gripper2base`：位置用 `L3·(cos t4, +sin t4)`，姿态却用 `Rz(t1)@Ry(+t4)`。
   而 `Ry(a)·(1,0,0) = (cos a, −sin a)` —— **符号天生相反**。
   算一下两者夹角：点积 = cos(2t4)，θ4=32° 时 **−0.438**、θ4=41° 时 −0.139、θ4=50° 时 +0.174，
   即"姿态认为的工具轴"和"位置认为的连杆方向"差 **116° / 98° / 80°**，且三档之间变化 36°。
4. 量级核对：目标距腕点约 25cm，36° 的姿态误差 ⇒ 最多 15cm 漂移，与实测 P 极差 10.5cm 同量级；
   而舵机下垂（1~2°）只能给 3~5mm，差一个数量级 —— 所以不是"机械松动/回差"。

**根因**

`fk_gripper2base` 的姿态把俯仰写成了 `Ry(+t4)`，而位置公式（`+sin`）隐含的是 `Ry(−t4)`。
两者互为镜像 ⇒ 末端坐标系的转动方向与真实连杆相反。手眼标定的旋转方程
`R_A·R_X = R_X·R_B` 只依赖姿态，镜像后**无论怎么摆都凑不出常量 X**，于是残差全部堆到平移方程上。
`handeye_geometry.Kinematics.fk` 是照着这份抄的，同一个错（注释里还写着"与 handeye_calib 一致"）。

为什么一直没被发现：`selftest` 第 1 组只比**位置**（对 `ArmIK.forward`，误差 0.000cm 全绿），
位置公式本身是对的，所以自检把 bug 放过去了。**只验位置不验姿态，是这次最大的教训。**

**解决**

1. `handeye_calib.fk_gripper2base`：`R = (_rz(t1) @ _ry(-t4))[:3, :3]`。
2. `handeye_geometry.Kinematics.fk`：同一个修改（`Ry = [[c4,0,−s4],[0,1,0],[s4,0,c4]]`）。
3. `selftest` 新增**第 1b 组**：扫 θ1/θ4 各档，断言 `dot(R[:,0], L3指向) == +1`（修后全为 +1.0000）。
   这条自检是"以后谁再把符号写反就立刻红"的锁。
4. 新增 `check_rot.py`：不依赖 X、不依赖连杆尺寸，直接比 `θ_A(FK)` 与 `θ_B(相机实测)`。
   原理是相似矩阵迹相同 ⇒ `θ_A ≡ θ_B`；比值偏离 1 就是脉宽↔角度映射错了，比值散就是相机没刚性固定在 J4 上。
5. **不用重采、不用摆臂**：PnP 原始数据没变，只需 `refk_samples.py` 按 `pulses` 重算机器人侧位姿，
   再对重算后的样本 `solve`（见第 11 条——直接对旧 `samples.json` 重跑 `solve` 是**无效**的）。

3. `refk` 对同一输入**幂等**（结果只取决于 `pulses`），跑一次和跑十次一样，可放心重复。
4. 本机用合成数据做端到端验证：故意用旧 FK 写 `R_gripper2base` → 直接 `solve` 得

### 第 13 条 · 系统报 24.7cm、皮尺量 30cm：不是尺度错，是缺一把「不依赖视觉的锚点」

1. **先查最可疑的 `square_m`**：让用户用尺子量旧手机屏幕棋盘的 10 格总宽，量出 **82mm**

3. **换一个完全不用视觉的锚点**：X 的平移模长 `|t|` 物理上就是「相机光心 → 夹爪尖」的刚体距离。
   核代码确认末端点定义：`fk()` 里末端点 = 走完 `L3` 的终点，**就是夹爪尖**（`handeye_geometry.py` 第 274 行）

镜头前端面比光心靠外 3~4mm，所以 `17.0 − 0.004 ≈ 16.6cm`，与解出来的 **16.67cm 吻合到 4mm**。

**解决**：
- ✅ **绝对尺度封死**：`square_m=0.0082`、`f=808.26`、`X` 全部正确，**不用重采、不用重打棋盘**。

- 剩下的 4.4cm 缺口回到**口径**，两个候选都能填到 3mm 内（都不改变系统正确性）：
  ① 底座 9×8.8cm、转轴居中 ⇒ 前边缘到转轴 **4.40cm**，`25.64+4.40 = 30.04`；
  ② 量的是棋盘**远边**而非中心（82mm 半宽 4.1cm），`30−4.1 = 25.9`。
- 判据固化：**以后凡怀疑绝对尺度，先量 `|t|`** —— 比棋盘、比差分、比卷尺都快、都硬，
  且一把尺子、30 秒、不动代码。

**面试说辞**：手眼标定的绝对尺度没法自证 —— 残差 1.6mm 只说明方程拟合得好，不说明 X 是真的。
我一开始被"皮尺 30cm vs 系统 24.7cm"带偏，去查棋盘格边长、查焦距，全是死路（还把棋盘 PDF 都打了）。

实测量 17.0cm，解出来 16.67cm，差 4 毫米，尺度这才封死 —— 顺带还证明了 AX=XB 里那个尺度自校正因子 0.755
是对的（如果不乘，平移会差 5cm）。

### 1 根因：为什么「必须重标」是伪冲突

#### 1.1 X 是什么（概念双轨）

- **大白话**：相机骑在手腕上，它看到的「那个点」要换算成手臂该往哪伸；X 就是这把换算尺子。
- **规范定义**：eye-in-hand 手眼标定求解 `AX = XB`（Tsai-Lenz / Park-Martin，IEEE Trans. Robotics & Automation 1989）。
  `X ∈ SE(3)` 是**相机坐标系相对末端执行器（gripper）的刚体变换**；
  `A` 是基座↔末端两次运动间的变换，`B` 是相机↔标定目标两次观测间的变换。

**不变量**：只要相机与机械臂**刚性固连在同一车架**上，车体整体平移、转向都只是把
「基座坐标系」搬到新的世界位置，**相机↔末端的相对关系 X 在刚体意义下不变**。
会变的是 `W`：基座↔世界（棋盘 / 桌面平面 / `--plane-z`）的注册。

> 佐证：项目早期方案（原文已随 2026-11-21 文档整理归档）阶段 1 就是「臂固连底盘、眼在手相机装末端；做手眼标定(求解 X)」，
> 说明「上车 + X」在原规划里本就是同一阶段，不是互斥项。

#### 1.2 但项目的 X 不是纯刚体不变量 —— 这点必须诚实

`handeye_X.json` 是**台架单点实标**的等效变换，已经混入台架几何假设：
12 组姿态、`tilt≈41°`、桌面 `z=0`、`--plane-z`、J2 下垂 `SAG_DZ=−3.88` / `TIP_BIAS_XY=(0.10,−0.95)`、
以及出口经验系数 `_EYE_RADIAL_K=1.091`。
`MEMORY.md` §4 明确写「**X 与 k 只在单次上电、同一姿态族、同一时段有效**」；
`docs/00-项目总览与硬数据速查.md` §10 也写「换姿态 / 换棋盘 / 换相机安装 / 重标 X / tilt 离开 41° ⇒ 系数全部失效，必须重测」。

⇒ 所以**不能假定台架 X 在车上仍准**。但正确处置不是「重标 X 去凑精度」——
那是 §4 明令禁止的动作；正确处置是「**封存台架 X，车上另做一次适用性验证并单独记录**」。

#### 1.3 精确结论

- **失效对象**：① 世界注册 `W`；② 车架振动 / 倾斜下的等效姿态与下垂量；③ 精度口径（数字不能外推）。
- **不失效对象**：X 的刚体定义（前提：车架刚度足够，见 §3.3）。
- **「车上视觉引导是坏的」的真实前提**：不是「没重标 X」，而是「没新增位姿注册 `W` 与停稳门控」。

#### 3.1 车体位姿注册 `W`（真正缺的东西）

#### 3.2 停稳门控

  并在文档里如实标注这是替代方案。
- 门控失败 ⇒ `return 2` 拒发，沿用项目既有的三条入场闸门风格（不给 `--plane-z` 强制 0.0 / 非 C 姿态拒 / 成功提示回位）。

#### 3.3 结构刚度验证（**先做这个，而不是先标定**）

- 这是让 X 是否仍成立的前置条件：玻纤板 + 铜柱 + 臂举起时重心高 ⇒ 车架可能弹性扭转，
  那相机↔基座就不再是理想刚体，X 才真的漂。这是**结构问题，不是标定问题**。
- 不上电阶段（沿用 §10 阶段①）：称重（日志估 **2.3~3.0 kg**）、倾斜测试、
  **推车前后各拍一张 `look.jpg` 对比棋盘像素位置**，位移超阈值先加固支架，不谈标定。

### 4 概念双轨速查

| 概念 | 大白话 | 规范定义 |
|---|---|---|
| 手眼矩阵 X | 把「相机看到的」换算成「手臂坐标」的尺子 | `AX=XB` 中 `X ∈ SE(3)`，相机↔末端刚体变换（Tsai-Lenz / Park-Martin） |
| 世界注册 W | 车停在哪、目标在车前方多远 | 基座坐标系↔世界坐标系的外参 `W ∈ SE(3)`，每次停车重新确定 |
| 刚体 / 不变量 | 两样东西焊死在一起，怎么搬相对位置都不变 | 刚体变换群 `SE(3)` 作用不改变两点间相对位姿 |
| 里程计 | 靠数轮子转了多少圈猜走了多远 | wheel odometry，由编码器脉冲积分估计位姿；打滑⇒无界漂移（无绝对观测） |
| 重力下垂 | 臂伸出去会微微往下掉一点 | 开环稳态误差 δ2=6.5° / δ3=2.2°；末端 C 姿态 dz −3.88 cm |
| 刚度 | 支架硬不硬，推一下会不会扭 | 结构抵抗弹性变形能力 `k = F/δ`；不足则破坏刚体假设 |
