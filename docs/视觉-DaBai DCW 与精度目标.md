### 二、关键原理（这一步决定后面能不能跑通）

DaBai / DaBai DCW / DaBai DW / Astra mini Pro / Gemini E 这些型号走的是 **OpenNI 私有协议**，不是标准 UVC：

- 深度传感器在设备管理器里表现为厂商自定义设备（Class_FF），Windows 不认识 → 必须装 `SensorDriver`；
- **Orbbec SDK v2 不支持这些老协议设备**，只支持 UVC 设备（Gemini2、Gemini2 L/XL、Femto 系列、Astra2、Gemini 330 系列等）；
- 所以这支相机只能用 **Orbbec SDK v1.x** + 私有驱动，别去装 v2 的 `pyorbbecsdk2`，会连不上。

### 三、Windows 检测流程（4 步，按顺序做）

```powershell
Get-PnpDevice -PresentOnly | Where-Object { $_.InstanceId -match 'VID_2BC5' } |
    Select-Object Status, Class, FriendlyName, InstanceId
```

正常输出应有三行且 `Status` 全为 `OK`。若深度那行是 `Error` + `Problem=28`，说明驱动没装。

### 四、Windows 上重装/排障的完整动作

1. **装驱动**（管理员）：
   `...\OrbbecSDK_v1.10.27\Driver\SensorDriver_V4.3.0.22.exe`
   装完若设备仍带感叹号，把相机拔插一次，或执行 `pnputil /scan-devices`。

2. **注册时间戳（可选，做 D2C 对齐时需要）**：
   管理员 PowerShell：
   ```powershell
   cd "D:\简历\STM32项目\4.ESP32-S3项目\工具\Orbbec_v1.10.27\SDK\OrbbecSDK_C_C++_v1.10.27_20250925_0549823cb_win_x64_release\OrbbecSDK_v1.10.27\Script"
   Set-ExecutionPolicy -ExecutionPolicy RemoteSigned -Scope CurrentUser
   .\obsensor_metadata_win10.ps1 -op install_all
   ```
   > 换一台电脑或换一个型号都要重新跑一次；不注册的话时间戳异常，深度-彩色同步会出问题。

3. **确认不是带宽问题**：当前是 `USB2.0`。DaBai DCW 本身就是 USB2.0 设备（深度 640×400@15 + 彩色最高 1080p@15），单开没问题；**同时开彩色 1080p + 深度**时若掉帧，优先把相机从 Hub 上拔下来，直插主板后置 USB 口（别插前面板、别串 Hub）。

### 五、OrangePi Kunpeng Pro（aarch64 Linux）上的检测

同一支相机接到开发板，流程不一样（没有 Windows 驱动这回事，靠 udev 权限）：

```bash
# 1) 枚举确认
lsusb | grep -i -E "2bc5|orbbec"
# 期望看到：2bc5:055c（RGB/复合）与 2bc5:065c（Depth）

# 2) 权限规则（不装规则就得每次 sudo）
cd OrbbecSDK_v1.10.27/Script
sudo chmod +x install_udev_rules.sh
sudo ./install_udev_rules.sh
sudo udevadm control --reload && sudo udevadm trigger
# 之后拔插一次相机生效

# 3) USBFS 缓存（多流/高分辨率必须调，默认 16MB 不够）
cat /sys/module/usbcore/parameters/usbfs_memory_mb
sudo sh -c 'echo 128 > /sys/module/usbcore/parameters/usbfs_memory_mb'
# 永久生效：/etc/default/grub 的 GRUB_CMDLINE_LINUX_DEFAULT 追加 usbcore.usbfs_memory_mb=128

# 4) 安装包（用 arm64 版，不是 amd64）
#    OrbbecSDK_v1.10.27_arm64.deb  →  dpkg -i 后直接敲 OrbbecViewer
```

注意：Kunpeng Pro 是 aarch64，Orbbec 官方 arm64 包主要按 Ubuntu 18/20/22 + Jetson 验证，装完先跑 `OrbbecViewer` 或 `hello_orbbec` 确认能开设备；如果库依赖不满足（libudev/libusb 版本），按 `ldd` 缺什么补什么。

### 一、总体结论

**相机本体功能全部正常，取流链路可用。** 48 + 16 + 10 项检查中，所有失败项经复核均为"测试脚本自身的判定标准/类型转换问题"或"该能力本就不支持"，**没有一项是相机硬件或驱动缺陷**。

> **最重要的一条自我纠错**：初版结论里的「640x480 双流 0 帧」是我代码 bug，不是相机缺陷。裸 API 显式指定 `Y11 + MJPG` 后，640x480 在 5/15/30 fps、与 320x240 / 640x360 混配下**全部 both=8 通帧**；关掉 D2C 对齐时 12/12 帧、有效率 80.6%。真正不支持的是该分辨率下的 D2C 对齐（`AlignFilter` 静默返回空）与内参上报（`approx=True` 回落 FOV）。`_pick_profile` 已改为按传感器类型分流格式串。

但实测出 **4 条硬能力边界**，必须写进使用约束（见第五节）。

| 功能 | 状态 | 实测证据 |
|---|---|---|
| 设备枚举 / udev | 正常 | Gemini E / 14618B 规则已装 |
| 深度取流 | 正常 | 30/30 帧，640x360 Y16 |
| 彩色取流 | 正常 | 30/30 帧，MJPG→BGR 640x360 |

### 二、能力枚举（实测可用档位）

**深度** 9 档：`160x120 / 240x180 / 320x180 / 320x240 / 480x360 / 512x384 / 640x360 / 640x480 / 1024x768`（Y11 / Y12 两种格式，5/10/15/30 fps）

**彩色** 8 档：`320x180 / 320x240 / 640x360 / 640x480 / 1280x720 / 1280x960 / 1440x1080 / 1920x1080`（BGRA / MJPG / RGB / YUYV 四种格式）

**双流可用交集**：`320x180 / 320x240 / 640x360 / 640x480`（四档都能双流出流；640x480 只是不能做 D2C 对齐）

> 结论：**640x360@30 是唯一「高帧率 + 双流 + D2C 对齐 + 设备真内参」的配置**，与当前 `source.py` 默认一致。

> **修正说明（复测后）**：初版把「640x480 双流」记为 0 帧并判为设备限制，复测证明是**自家 `_pick_profile` 的格式顺序 bug**（把 MJPG 拿去试深度，拿到非法组合）。修复后 640x480 双流可出帧；真正不支持的是**该分辨率下的 D2C 对齐**（`AlignFilter` 静默返回空、`get_camera_param()` 不给内参）。

### 三、关键量化数据

#### 3.1 深度精度随距离（时间噪声，25~30 帧同一像素标准差）

| 距离区间 | 时间噪声（中位） | 相对噪声 |
|---|---|---|
| 0.25~0.8 m | **1.49 ~ 3.42 mm** | 0.26% |
| 1.0~1.5 m | 7.14 mm | 0.57% |
| 1.5~2.5 m | 17.60 mm | 0.84% |

#### 3.2 深度是**量化输出**（重要）

对 2.1m 处墙面连续采 60 帧，中心像素只出现 3 个码值：`2068 / 2112 / 2159`，

- **量化台阶 ≈ 44 mm**（中位 46mm）
- 极差 91 mm，标准差 17.7 mm

台阶与距离平方近似成正比（视差量化特性）：

| 距离 | 预测台阶 q ≈ 1.1e-5 · z² |
|---|---|
| 0.3 m | ≈ 1.0 mm |
| 0.5 m | ≈ 2.8 mm |
| 1.0 m | ≈ 11 mm |
| 2.0 m | ≈ 44 mm |

> 抓取应发生在 **0.3~0.6 m**，此时精度 mm 级；2 m 处 ±22mm 是物理上限，不是故障。

#### 3.3 有效深度覆盖（640x360 对齐到彩色）

| 区域 | 有效占比 |
|---|---|
| 全图（对齐后） | 64.3% ~ 67.5% |
| 中央 50% | **88.5%** |
| 中央 20% | **99.0%** |
| 左侧约 160 px（1/4 宽） | **≈0%** |
| 原始深度（不对齐） | 全图 83.2%，中央50% 98.2% |

逐列有效占比（每 32 列，从左到右）：
`0.13 0.08 0.00 0.05 0.10 0.29 0.79 0.93 0.99 0.99 1.00 0.89 0.83 0.87 0.91 0.83 0.82 0.85 0.86 0.65`

> D2C 重采样会吃掉边缘约 19 个百分点（83.2%→64.3%），**中央区域几乎不受影响**。

#### 3.4 D2C 对齐精度

用「彩色 Canny 边缘 ↔ 深度 Canny 边缘」做 ±12px 平移搜索，两轮结果：

- 第 1 轮：最佳 `(dx=-2, dy=-2)` 18.6%，`(0,0)` 15.6%
- 第 2 轮：最佳 `(dx=-4, dy=-4)` 20.0%，`(0,0)` 17.1%

> 残差 2~4 px。2m 处横向约 1~2 cm；0.5m 处约 0.3~0.7 cm。
> 边缘重合率绝对值低是**指标设计**问题（墙面纹理有彩色边缘但无深度阶跃），不是错位。

#### 3.5 深度量程（当前场景）

`min=299 mm / P1=579 / P50=2068 / P99=2159 / max=2258 mm`

### 五、能力边界与使用约束（务必遵守）

| # | 约束 | 影响 | 对策 |
|---|---|---|---|
| 1 | 深度有效区：曾测到左侧 1/4 为 0% | 复测激光开启后左侧 1/4 有效率 0.83，早前 0% 无法复现 | **目标放画面中央**，中央 20% 有效 99% |
| 2 | 深度是量化输出，台阶 ∝ z² | 2m 处 ±22mm | 抓取控制在 **0.3~0.6m**；用区域中值而非单像素 |
| 3 | 640x480 下**无 D2C 对齐、不报内参** | 出流正常（关对齐 12/12 帧、有效率 80.6%），但深度网格 ≠ 彩色网格，像素→3D 会算错 | **固定 640x360@30**；`warmup_ok=False` 时不是相机故障，换回 640x360 |
| 4 | 只能对齐到彩色，不能对齐到深度 | 不能以深度为主网格 | 保持 `AlignFilter(COLOR_STREAM)` |
| 5 | 硬件帧同步不支持 | `synced` 恒 False | 已不调用 `enable_frame_sync()`（调了会拖坏彩色流） |
| 6 | USB2.0 带宽 | 29.7 fps 上限 | 不追求高分辨率/高帧率 |
| 7 | 黑色/高反光物体无回波 | `sample_region` 返回 None | 已被 `depthproc` 的 `min_valid_ratio` 处理 |

### 五之二、设备侧参数调优（2026-11-19 深夜复测）

本轮把 SDK 暴露的 30 个可读写属性逐个过了一遍，找到 4 个真正影响深度质量的开关。

| 参数 | 结论 | 证据 |
|---|---|---|
| `OB_PROP_LASER_BOOL` | **必须开**（现为默认） | 同场景两轮 A/B：关=有效像素 **0.000**；开=全图 0.925 / 中央20% 0.999 / 左侧1/4 0.832 |
| `MIN/MAX_DEPTH` | 抓取建议 200~1200 | 钳位后超量程区域（2.2m 墙）诚实变 0，中央20% 有效 0 |
| `DEPTH_HOLEFILTER_BOOL` | **钳位时必须关** | 开着钳位时，2.2m 的墙被填成 **1477mm 假有效值**，在 `sample_region` 眼里就是假障碍物 |
| `DEPTH_PRECISION_LEVEL_INT` | 0 已是最优 | 0=近场 38348 px / 1.43mm；2=11105 / 47mm；4=1129；6=0（全空） |
| `DEPTH_AUTO_EXPOSURE_BOOL` | 保持 True | 固定曝光残留会让换光照后整片过曝/欠曝 |
| `set_align_mode(HW_MODE)` | **不可用** | 硬件对齐能出帧，但残差最优点落在 ±10px 边界（dx=10）；软件 `AlignFilter` 是 (0,-2) |

**粘性属性陷阱**（本轮实际踩到）：`MIN/MAX_DEPTH`、曝光、增益都是掉电保留的。
上一轮实验把量程设成 200/1500、曝光锁 1200 后，下一次 open 仍带着这些值，
表现为"深度莫名被截断""整片偏暗"却查不出原因。现在 `DepthCamera.__init__`
在未显式指定时会主动复位（量程 0/10000、自动曝光 True），并在 `get_props()` 里可查。

**分阶段耗时**（3 核 aarch64，640x360@30）：

```
wait_for_frames 20.39ms | align.process 10.54ms | depth 转换 0.48ms | MJPG 解码 2.06ms
合计 33.47ms -> 上限 29.9fps（30fps 流本身即上限，已跑满）
```

对齐占 10.5ms 是大头，但硬件对齐不可信、自研 D2C 更慢，**保持软件对齐**。
`read(with_color=False)` 可省 2ms；`read(drop_stale=1)` 可在消费者慢时丢掉陈旧帧。

### 六、对明天手眼标定的直接影响

1. **内参可直接用设备上报值**：fx=fy=358.476、cx=319.669、cy=179.010、640x360，`approx=False`，标注 `source='device'`。不需棋盘重标（除非要畸变系数）。
2. **深度内参与彩色内参完全相同**（`depth_intrinsic` == `rgb_intrinsic`），说明 SDK 给的是对齐后彩色网格口径 —— 与 `localize.pixel_to_camera` 的假设一致。
3. **标定板/目标必须放在画面中央 50%（有效 88.5%）**，别看左半边。
4. **对齐残差 2~4px** 建议现场复核：把一个纸箱棱边放在 0.4~0.5m，跑一次边缘叠加，若残差 > 8px 再考虑重标内参。
5. `depth_intrinsic` 无法验证深度原生 FOV（79°/62° 是 4:3 规格，而当前是 16:9 裁切），**不要再拿 79/62 去卡 640x360 的内参**。

## 三、视觉-DaBai DCW 与精度目标

> 来源：`视觉-DaBai DCW 与精度目标.md`

> 背景：小Z 曾确认"想要精确到毫米级别"，但最新决策（2026-11-02）为**控制成本、复用既有舵机**，机械臂执行器定为 **4× 25kg 数字舵机 + 2× MG996R（均为 PWM 开环舵机）**，放弃原计划的 STS3215 总线舵机升级。本文把现有 PWM 方案的精度天花板算清楚，并保留达到毫米级的三档升级路径（当前均未采用）。**核心结论：PWM 开环舵机在物理上无法达到毫米级，瓶颈是执行器（齿轮回差 + 无位置反馈），不是相机。**
>
> 🔴 **2026-11-21 订正**：① 相机基线已改为 **DaBai DCW 深度相机**（眼在手，0.299~2.258m 实机），下文「双 GF100」段落作废；② 总线舵机**二手件已购**（HTS-35H / HTD-45H / LX-224HV，`servo_bus.c` 骨架已写、未接线），不再写「已取消 / 未采用」；③ 当前实机仍为 PWM 开环，故本文的精度天花板结论仍成立。

---

### 一、先说人话：精度分两种，别混

> **概念·重复定位精度（大白话）**：机器人把臂末端送到同一个目标点，反复送 10 次，这 10 次落点之间差多少。差得越小越"稳"。
> **规范定义**：Repeatability = 在相同条件下，机械臂末端执行器多次到达同一指令位姿时的离散程度（标准差或最大偏差），单位 mm；由关节编码器/反馈分辨率、齿轮回差、结构刚性决定，与"标不标定"无关。

> **概念·绝对定位精度（大白话）**：目标在真实空间里是 (x,y,z)，机器人认为自己到了 (x,y,z)，实际差多少。这包括了"重复定位准、但整体偏了"的情况。
> **规范定义**：Accuracy = 末端实际位姿与指令位姿之间的系统偏差，单位 mm；取决于运动学建模误差 + 手眼标定残差 + DH 参数误差，可通过标定补偿一部分，但永远有下限。

**一句话**：重复定位是"稳不稳"，绝对精度是"准不准"。毫米级通常指**绝对定位精度 ≤ ±1mm**。

---

### 二、现有配置的天花板（基于已确认硬件）

已确认事实（见 `硬件清单与接线.md` 第 88 / 254 行，2026-11-02 最新决策）：
- 机械臂 = **六自由度舵机机械臂，执行器 = 4× 25kg 数字舵机（PWM 开环）+ 2× MG996R（PWM 开环），共 6 路标准 PWM（50Hz / 0.5~2.5ms）**
- 相机 = **DaBai DCW 深度相机（眼在手）✅ 已实机**；GF100 单目作备用，第二颗不再采购（2026-11-21 订正）

各环节误差量级（实测经验值）：

| 环节 | 误差量级 | 说明 |
|---|---|---|
| GF100 像素分辨率 | **0.3~0.5 mm/像素**（0.3m 处） | 相机底子够，远在 ±1mm 目标线下 |
| 镜头畸变（标定后） | ~0.5~1mm | 无畸变镜头 + 标定可压到压线 |
| **舵机臂重复定位（PWM 开环）** | **25kg 数字舵机轴 1~3 mm；MG996R 轴 3~5 mm** | 舵机内部自带位置伺服、MCU 无反馈；误差来自齿轮回差 ±1~3°，臂展 20~30cm 时末端累积到 cm 级 |
| **手眼标定残差（新手）** | **5~20 mm** | 标定板采集姿态不够多/均匀时最差 |
| **整体闭环绝对精度** | **≈ cm 级（5~20mm）** | 由最弱环节决定，相机再好也补不上 |

> ⚠️ **结论钉死**：GF100 分辨率已达亚毫米/像素，换更贵的相机**完全弥补不了舵机臂的 cm 级误差**。要毫米级，第一步必须换执行器。

### 三、达到毫米级的硬件升级路径（三档）

> 📌 **当前选定方案（2026-11-02）**：机械臂执行器 = **4× 25kg 数字舵机 + 2× MG996R（PWM 开环）**，下面三档均为**可选升级路径、目前均未采用**。当前演示为 **cm 级**，足够展示系统级能力；毫米级是「以后有钱/有需求再升级」的路线，不是当前承诺。

#### 方案 A · 总线舵机升级（低成本，到 1~2mm）★ 可选升级路径（当前未选）★
- **做法**：把 6 路 PWM 开环舵机换成**带磁编码反馈的闭环总线舵机**。实测选型 **Feetech STS3215**（7.4V/19kg.cm、12-bit 磁编码、≈0.088°/LSB、半双工 UART 1Mbps、反馈位置/速度/负载/电压/温度/电流），STM32 通过半双工串口（DIR 脚切收发）下发角度+读回实际位置，形成闭环。驱动需在升级时新增；当前 PWM 方案见 `Core/Src/pca9685.c`。
- **精度**：单关节重复定位由 PWM 开环舵机的 ±1~3°（机械臂末端 cm 级）降至 **±0.3° 以内**，臂展 25cm 时末端约 **1~2mm**。
- **成本**：STS3215 国内零售 **99 元/个**（2026-11-02 飞特官网核实），6 个 ≈ **¥600**；若选更大扭矩款 LDX-227（20kg.cm，约 ¥150~200/个）则 ≈ ¥900~1200。比此前预估（¥900~2100）更低。
- **工程量**：中。需从当前 PWM 舵机驱动（`Core/Src/pca9685.c`）切换到 UART 总线协议 + 位置回读 + 堵转保护；接线须舵机电源与 MCU 逻辑电源**分离**（堵转 2A/颗会拉塌 UART 电平）。
- **适配**：A 档精神不变（仍是舵机臂本体，不换结构），但精度上一个量级。

#### 方案 B · 步进/伺服 + 谐波减速（中成本，亚毫米）
- **做法**：每关节用 **42 步进电机 + 谐波减速器（减速比 50~100）+ 编码器闭环**，或交流伺服。彻底告别舵机的回差问题。
- **精度**：单关节角分辨率达角秒级，末端 **<0.5mm**（接近 ±0.2mm）。
- **成本**：六轴套件（含谐波）约 **¥2000~5000**。
- **工程量**：高。需重新设计机械臂结构（电机+谐波尺寸大、重），电机驱动板、闭环控制算法都要重做。
- **适配**：机械臂本体大改，已超出"复用既有项目"的初衷。

#### 方案 C · 工业协作臂（高成本，±0.02mm）
- **做法**：直接采购成品协作臂（遨博 i 系列 / 节卡 / 越疆），自带控制器与高精度标定。
- **精度**：标称 **±0.02~0.05mm**。
- **成本**：**¥2 万~8 万**。
- **工程量**：低（开箱即用），但项目"自研硬件"的含金量被稀释——面试官会问"臂是你做的吗"。
- **适配**：仅当你要真做工业级演示、且不在意"臂非自研"时。

### 七、决策建议（2026-11-02 最新）

- **当前决策已定**：机械臂用 **4× 25kg 数字舵机 + 2× MG996R（PWM 开环）**，做到 **cm 级系统演示**即可；精力放在"云-边-端全栈 + 自研硬件"的差异化上，不砸钱追毫米级。这是有意为之的成本控制，不是做不到。
- **若日后真要毫米级演示**：从**方案 A（总线舵机，~¥600 起）**起步，性价比最高，且仍保留"臂驱动自研"的含金量；视觉侧补全局快门相机 + Astra S + 标定板（再加 ~¥1200）。
- **方案 B/C 仅在确有工业级需求时考虑**，会显著偏离"复用既有项目、低成本自研"的初衷。

> 本决策与"范围锁死 A 档（不买雷达/深度做导航 3D）"不冲突：A 档管"做什么功能"，本文管"抓取精度到哪"，是独立的一笔可选投资；当前投资级别 = 0（复用既有舵机）。
