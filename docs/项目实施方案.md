# 移动操作机器人（眼在手 + 多视角）云-边-端·IoT 协同系统 — 项目实施方案

> **项目定位**：第四个求职作品集项目，也是小车 + 机械臂两个既有项目的**融合升级版**。把六自由度机械臂装到智能小车底盘上，构成"会跑的机器臂"——移动操作机器人（mobile manipulator）。用 **KunPeng Pro（边/云）+ ESP32-S3（端交互）+ STM32F407（端执行）** 构建一套"感知-决策-行动-运维"全闭环的具身智能系统，并叠加 **IoT 端-边-云贯通的可观测与远程运维能力**，让整套系统不止"能用"，而是"可监控、可告警、可远程升级、可长时间无人值守运行"。
> **核心价值**：一个人扛下"从硅到云到运维"全栈——硬件 PCB / 电机驱动 + RTOS 实时控制 + 视觉伺服 + 眼在手标定 + 边缘 AI 部署 + Linux 服务 + 全栈 Web + 移动端交互 + **IoT 设备全生命周期管理（端-边-云协同、时序可观测、OTA）**。对标 2026 企业最稀缺的"既懂算法又懂硬件还懂运维"复合人才（行业缺口约 100 万，系统培养的本科生最早 2030 年才毕业）。
> **为什么不普通**：不是小智 clone / ROS2 demo（培训机构已堆满），而是 **移动平台 + 眼在手 + 多视角视觉 + 云-边-端异构协同 + 语音→动作映射 + IoT 全生命周期可观测** 的真系统。固定基座机械臂已属常规，移动操作 + 眼在手标定 + 手机/网页交互 + 工业级 IoT 运维才是 2026 具身智能最硬核的落地方向（行业从"固定机械臂"转向"移动+操作+可运维"组合，2026 上半年国内具身智能融资 935 亿、同比 5 倍）。
> **状态**：2026-10-31 方向升级为"移动操作机器人 + 眼在手 + 多视角 + 云-边-端协同"，此前"固定基座具身机械臂""桌面宠物"方案作废；同日追加 **IoT 端-边-云重度融合**。2026-10-31 深夜**可行性核查**：主栈 EMQX / eKuiper / InfluxDB / Grafana 均有官方 arm64 镜像，KunPeng Pro(aarch64, 鲲鹏920 自研 TaiShan 核) 可原生跑；**ThingsBoard CE 核心节点官方镜像主要为 amd64，KunPeng 本地跑需 qemu 模拟、不稳**，故云端平台改推「阿里云 IoT / EMQX 桥接 + 自研看板」，ThingsBoard 仅作可选对比（已规避坑）。NPU 不可用已确认，不影响本项目。

## 一、系统架构（移动操作 + 云-边-端·IoT 协同）

```
[手机 / 网页]  WebSocket / MQTT  ←┐
  摇杆 / 点选抓取 / 语音按钮        │
                                   ▼
[云]  IoT 平台（首选阿里云 IoT：现成设备影子/规则引擎/OTA）
   ├─ 设备影子(device shadow)：期望态↔实际态对齐
   ├─ 规则引擎：遥测→存储→告警→通知(微信/邮件/钉钉)
   ├─ OTA 固件管理：版本/灰度/回滚
   └─ 远程监控大屏：设备列表/实时状态/控制面板
        ▲ EMQX 云桥接(over TLS)              ▲
[边]  KunPeng Pro v1.1  (openEuler 22.03, 4核 ARMv8-A(鲲鹏920) aarch64, 16GB)
   ├─ 视觉感知 : 顶部全局相机(找目标/导航) + 眼在手相机(精细位姿)
   ├─ 任务规划 : 接收语音/点选 → LLM 分解为"导航 + 抓取"动作序列
   ├─ 通信中枢 : WebSocket(语音流/控制) + MQTT Broker(EMQX) + 串口/CAN(底层)
   ├─ IoT 网关 : 边缘规则引擎(eKuiper) + 串口/CAN↔MQTT 协议桥 + 断网本地缓存
   ├─ 时序管线 : 遥测 → 规则引擎 → InfluxDB → Grafana 看板
   ├─ 自研看板 : FastAPI + SQLite（复用 Web 能力，替代重体量 ThingsBoard）
   └─ Web 数字孪生看板 + 任务/异常日志库
        ▲ WebSocket / MQTT                    ▲ 串口 / CAN（经 USB-TTL / USB-CAN 适配器）
[端-交互] ESP32-S3                      [端-执行] 小车 STM32 + 机械臂 STM32
   ├─ INMP441 I2S 语音采集                   ├─ 小车底盘：运动/里程计/对准
   ├─ WakeNet9 离线唤醒(向量指令)            ├─ 机械臂：6 轴逆运动学/轨迹插值
   ├─ MQTT/CoAP IoT 客户端(上报/订阅)        ├─ 经边网关协议桥上云(串口/CAN→MQTT)
   ├─ WebSocket → KunPeng LLM               ├─ 接收 KunPeng 下发的导航/目标位姿
   └─ BLE / MQTT 配网 / OTA 无线升级         └─ 执行反馈(里程/关节电流)回传 KunPeng
        │
   [眼在手摄像头] ━ USB/CSI ━ KunPeng（随机械臂末端一起动）
   [顶部全局摄像头] ━ USB/CSI ━ KunPeng（看全工作区、导航对准）
```

**五层分工（面试必讲）**：
- **端-执行（双 STM32F407）**：硬实时域，确定毫秒级响应。一枚管**小车底盘**（运动控制 + 里程计 + 对准），一枚管**机械臂**（六轴逆运动学 + 轨迹插值）。作为 IoT 终端设备，**经 KunPeng 边网关协议桥（串口/CAN↔MQTT）上云**，上报里程、关节电流、到位状态，订阅导航/抓取指令。物理连接：STM32 的 UART/CAN → USB-TTL / USB-CAN 适配器 → KunPeng USB。
- **端-交互（ESP32-S3）**：无线 + 轻量 AI 域，干"人用嘴/手机指挥机器人"的活，是具身智能自然交互入口，同时是**直连 Wi-Fi 的 MQTT/CoAP IoT 客户端节点**（上报唤醒/网络/音频健康，订阅模式切换与 OTA）。
- **移动端（手机/网页）**：人机界面，WebSocket/MQTT 下发摇杆、点选、语音指令，实时回显相机画面与状态；并可通过云端 IoT 平台远程查看设备、接收告警。
- **边（KunPeng Pro）**：通用计算域 + **本地 IoT 网关**，跑视觉推理、LLM 规划、多视角融合、通信调度、Web 服务、自研看板，同时承载 EMQX Broker、边缘规则引擎、协议桥与断网缓存，是系统"大脑 + 局域网中枢"。
- **云（IoT 平台）**：设备全生命周期管理，**首选阿里云 IoT**（真云、零本地负担、现成影子/规则引擎/OTA）；或用 EMQX 桥接把数据上公有云。**不把 ThingsBoard 跑在 KunPeng 本地**（其 CE 核心镜像主要 amd64，aarch64 需模拟、不稳）。

## 三、核心技术含金量点（对标企业 JD，让面试官眼前一亮）

1. **移动操作（mobile manipulation）**：底盘导航 + 机械臂抓取联合求解，是固定基座机械臂的天然进化形态，2026 具身智能最猛方向。
2. **眼在手（eye-in-hand）手眼标定**：相机固连末端法兰，求解刚体变换满足 **AX=XB**；相对眼在手外标定更简单但有视野收放问题，是真实机器人学难点。
3. **多视角视觉融合**：顶部全局相机（找目标/导航对准）+ 末端眼在手相机（精细位姿），2-4 视角是工业移动操作标准做法。
4. **视觉伺服闭环（visual servoing）**：识别→位姿估计→逆运动学→轨迹→执行反馈，经典难题。
5. **异构多协议通信**：WebSocket（语音流/控制）+ MQTT（遥测/影子）+ CoAP（轻量保活）+ 串口/CAN（底层），跨"实时域 ↔ Linux 域 ↔ 无线域 ↔ 云域"协同。
6. **语音→动作的自然语言映射（VLA 雏形）**：LLM 把"把红色零件放进盒子"转成"导航到 A 区 → 对准 → 抓取 → 放置"结构化动作序列。
7. **移动端交互**：手机/网页 WebSocket 摇杆 + 点选抓取（图像像素→3D 相对坐标→逆运动学），BLE/WiFi 配网。
8. **边缘 AI 部署 + 全栈**：KunPeng（ARM aarch64）视觉推理 + 量化；Web 数字孪生看板 + 数据库。
9. **IoT 端-边-云全生命周期（重度融合，核心增量）**：统一设备模型 + 设备影子；MQTT 分级 QoS/遗嘱/保留消息；边缘规则引擎本地计算与断网自治；串口/CAN↔MQTT 协议桥；**InfluxDB + Grafana 时序可观测看板**（电量/温度/帧率/CPU/关节电流/任务成功率）；**OTA 远程固件升级**（ESP32 空中升级 + STM32 串口 IAP 双 bank，含签名校验与回滚）；TLS/mTLS 设备认证与安全运维。
10. **系统健壮性**：掉电恢复、断网续传、看门狗、OTA、本地缓存补传——"连续跑几千小时不出故障、坏了能远程修"。

## 七、端侧任务架构（面试必讲）

### 7.1 ESP32-S3 语音交互节点（FreeRTOS 双核）
- **双核划分**：Core 0 跑网络/协议（WebSocket/MQTT/BLE + OTA 任务）+ 音频输出；Core 1 跑音频采集 + WakeNet9 唤醒 + 状态机。
- **IPC**：音频帧用 `queue` 在采集→唤醒→网络间传递；状态机(idle/listening/thinking/speaking)用 `event group` 同步。
- **I2S 流水线**：INMP441(I2S RX) → 环形缓冲 → WakeNet9 检测 → 命中经 WebSocket 上行；MAX98357A(I2S TX) 播放 TTS。
- **IoT 客户端**：MQTT/CoAP 周期上报唤醒次数/网络质量/音频健康/任务计数，订阅 `cmd` 主题接收模式切换与 OTA 触发；演示阶段先用 Token/用户名密码，后续升级 mTLS 设备证书。
- **OTA**：`esp_https_ota` 从云端/边拉取签名固件，双分区(otadata)切换，失败自动回滚（ESP-IDF 原生支持，先落地）。
- **定位**：不是"主控宠物"，而是系统人机交互入口 + 直连云的 IoT 边缘节点。

### 7.2 小车底盘 STM32（实时运动 + 里程计 + 对准 + IAP）
- 编码器脉冲计数 → 里程计积分（位置/航向）；PID 速度闭环；顶部相机/IMU 辅助对准。
- 串口/CAN 接收 KunPeng 下发的导航目标(目标坐标/对准角度)，回传里程与到位状态；经边网关协议桥转 MQTT 上云。
- **串口 IAP 双 bank**（深度项）：边网关经适配器下发固件分片 → bootloader 写入备用 bank → 校验签名 → 切换；异常回滚，防变砖。先实现单 bank 简单 IAP 验证，再上双 bank + 签名。

### 7.3 机械臂 STM32（六轴实时控制 + IAP）
- 6 轴逆运动学 + 多项式轨迹插值 + 速度前瞻；FreeRTOS 多任务分级(运动/通信/传感)。
- 接收 KunPeng 下发的目标位姿(基座系或末端相对系)，执行并回传关节角/电流反馈；同享串口 IAP 双 bank 升级通道。

## 八、通信协议设计

| 协议 | 域 | 用途 | 要点 |
|---|---|---|---|
| WebSocket | 移动端/ESP32 ↔ 边 | 流式语音/文本/控制/视频流 | Opus 音频上行、TTS 下行、点选像素坐标上行 |
| MQTT | 端 ↔ 边 ↔ 云 | 遥测 / 影子 / 控制 / OTA | `device/<id>/state`(QoS1)、`device/<id>/cmd`(QoS1)、`device/<id>/shadow`(QoS1+保留消息)；LWT 遗嘱、retained |
| CoAP | ESP32 ↔ 边 | **轻量保活 / 低功耗状态上报** | 用于 ESP32 休眠/低功耗场景的轻量资源读写，省电；非常规节点可不用 |
| 串口 / CAN | 边 ↔ 端-执行 | 底层控制指令 + IAP 固件分片 | 导航目标/目标位姿下发、里程/关节反馈回传、固件分片传输（经 USB-TTL/USB-CAN 适配器） |
| BLE GATT | 移动端 ↔ ESP32 | 首次配网 | 手机配 Wi-Fi，配完断开 |
| HTTPS | 边/端 ↔ 云 IoT 平台 | OTA 固件拉取 / 影子同步 | TLS/mTLS 设备证书认证、固件签名校验 |

> **QoS 分级原则**（面试被问别说"全用 QoS2"）：控制/遥测用 **QoS1**（至少一次，够用且吞吐高）；影子状态用 **QoS1 + retained**（新订阅者立即可得最新态）；OTA 固件分片用 **QoS1 + 分片序号确认**（不用 QoS2，开销大、握手多）。LWT 遗嘱在端异常断线时自动通知云端"离线"。

## 九、风险与避坑

1. ✅ **ESP32-S3 核心板电容/电源已核对正确（无错误，无需修改）**：实际 BOM（ESP32-S3.xlsx）用 **U2=AMS1117-3.3**（1A，远超乐鑫 ≥500mA 要求）、3.3V 去耦 22µF+多颗 10µF/100nF，符合官方指南；**无 VCAP、未用 RT9193**（VCAP 是 STM32 内部稳压器专用引脚，ESP32-S3 无此引脚），故此前担心的"3 处电容错误"不适用于本板。回板可直接焊接，焊接检查表与排查小抄已就绪。
2. ✅ **RT9193-33GB 风险不适用本板**：核心板未采用 RT9193，改用 AMS1117-3.3（输出 1A 满足 Wi-Fi 峰值），瞬时下坠可控。若仍担心，可在模组 3V3 引脚附近并一颗 10~22µF 作保险（非必须）。
3. **NPU 不可用（已确认）**：KunPeng Pro 昇腾(Ascend) NPU（官方标称 8TOPS INT8）载板电流采样链路缺陷（LPM `sensor_type=0xd1` 走 SPMI 读不到电流，power=0.0，set_device 507033），计算面无法启用。本项目不依赖 NPU，当 ARM 服务器 + IoT 网关用。别卡时间。
4. **眼在手标定难度**：相机-末端坐标系变换，满足 AX=XB，是真实难点，需做标定流程并验证精度——"硬核"证据点，别跳过。
5. **小车定位漂移**：纯里程计会漂，需加视觉定位 / AprilTag 标记 / IMU 融合，才能"停到抓取范围内"。
6. **深度获取**：单目相机只有像素不知距离，需深度相机/双目或限定场景(已知桌面高度)。
7. **实时性抖动**：Linux 域(KunPeng)与实时域(STM32)间端到端延迟抖动，通信层需超时/重传/缓冲设计。
8. **整车功耗/电源**：KunPeng 吃几瓦，上车需电池 + 稳压，整车功耗续航要算；ESP32 可走 CoAP 轻量保活/浅休眠降功耗。
9. **多视角融合**：全局相机导航 + 眼在手精细，标定与坐标统一是工程重点。
10. **别只做到"能对话"就停**：必须打通阶段 6 闭环(语音/点选→规划→导航→抓取)才有得讲；阶段 7-9 IoT/可观测/OTA 是企业最看重的"工程化成熟度"证据。
11. **xiaozhi 等开源可白盒参考架构，别原样抄**：差异化在"系统是你设计的、每层都是你写的"。
12. **硬件双轨**：核心板已回板且 BOM 已核对正确（ESP32 用 AMS1117、STM32 电容值均对），焊接检查表与排查小抄已就绪，无硬阻塞；先用现成 DevKitC 跑软件、自研板并行焊接验证即可。
13. **STM32 上云的物理连接（新增）**：STM32 不直接联网，必须经 **USB-TTL / USB-CAN 适配器**接入 KunPeng，由边网关协议桥转 MQTT。适配器是必选硬件，架构图别画成"STM32 直连云"。
14. **IoT 安全与一致性（新增）**：MQTT 至少 Token/ACL，后续升级 mTLS + 设备证书；OTA 固件必须签名校验防刷机；断网期间遥测先写本地缓冲，重连后按时间戳补传，保证数据不丢、影子最终一致。
15. **⚠️ ThingsBoard 架构坑（新增，已规避）**：ThingsBoard CE 核心节点官方 Docker 镜像主要为 **amd64**，在 aarch64 的 KunPeng 上跑需 qemu 模拟、不稳且占资源。**云端平台改推阿里云 IoT（真云）或 EMQX 桥接 + 自研 FastAPI 看板**，ThingsBoard 仅作可选/对比，不本地部署。
16. **设备影子需自研（新增）**：EMQX 开源版**无现成设备影子**，需在 KunPeng 上自研轻量影子服务（用 retained message + 应用层合并 `desired`/`reported`），或直接用阿里云 IoT 现成影子。"端离线下发指令上线即执行"用它实现，别假设 Broker 自带。
17. **CoAP 别堆砌（新增）**：当前项目无真正休眠传感节点，CoAP 只定位为"ESP32 低功耗保活/轻量状态上报的可选通道"。简历写 CoAP 要能说清用在哪，否则像凑名词。
18. **OTA STM32 双 bank 是深度项（新增）**：ESP32 OTA 是 ESP-IDF 原生、先落地；STM32 IAP 双 bank + 签名校验要自己写 bootloader + 密码库(mbedTLS/tinycrypt)，工作量大。面试讲"OTA 升级闭环"时，先保证能展开 ESP32 部分，STM32 部分说清设计即可，别承诺没实做。
19. **端侧存储有限（新增）**：断网环形缓冲受 Flash/NVS 容量限制，先做"QoS1 + 重连重发"，环形缓冲作为进阶；别写"无限缓存"。
20. **优先级（新增）**：机器人主线（阶段0-6）优先于 IoT（7-9）；IoT 是加分不是主线。KunPeng 上 NOW 能搭的只有 EMQX+InfluxDB+Grafana 纯软件最小闭环，协议桥/OTA 需等硬件。

## 十一、IoT 端-边-云协同（可观测闭环，重度融合专节）

> 这一节是把"机器人系统"升级为"可运维产品"的关键，也是和培训班 demo 拉开差距的硬证据。核心是**统一设备模型 + 端-边-云数据闭环 + 全生命周期管理**。

### 11.1 统一设备模型与设备影子
- 每台设备（ESP32-S3 / 底盘 STM32 / 机械臂 STM32）有唯一 `deviceId`、型号、固件版本、能力标签。
- **设备影子（device shadow）**：云端/边保存 `reported`（实际态，端周期上报）与 `desired`（期望态，云端/手机下发）。断网重连后自动对齐——例如手机下发"移动到 A 区"，端离线时存 `desired`，上线即执行。
- **实现方式（关键）**：EMQX 开源版**无现成影子**，两种落地：
  - **方案 A（推荐，零依赖）**：用 EMQX `retained message` 存 `reported` + 自研一个轻量"影子服务"（Python/Go，订阅 `state` 主题、合并 `desired/reported` 存 SQLite/Redis、响应 `get` 请求）。
  - **方案 B（真云现成）**：直接用**阿里云 IoT** 的设备影子（平台内置，免自研），最适合简历演示。
- 双 STM32 不直接联网，由 **KunPeng 边网关做串口/CAN↔MQTT 协议桥**（USB-TTL/USB-CAN 适配器接入），把实时数据封装成统一遥测报文上云，对外暴露标准 IoT 设备接口。

### 11.2 MQTT 通信质量与可靠性
- **分级 QoS**：控制/遥测 QoS1（至少一次）；影子状态 QoS1 + retained（新订阅者立即可得最新态）；OTA 分片 QoS1 + 分片序号确认（**不用 QoS2**，开销大）；**LWT 遗嘱**在端异常断线时自动通知"设备离线"；**保留消息**缓存最新状态。
- **安全分阶段**：演示先用 Token/用户名密码 + ACL（每设备仅可发布/订阅自身主题）；后续升级 **mTLS + 设备证书**（防伪造与越权）。
- **CoAP**：定位为 ESP32 低功耗保活 / 轻量状态上报的可选通道（省电），非常规节点不用。

### 11.3 边缘-云协同 + 断网自治
- **EMQX(arm64)** 作边 MQTT Broker，支持规则引擎与**云桥接（bridge）**，把关键遥测转发到云端 IoT 平台（阿里云 IoT）。
- **边缘规则引擎（eKuiper, arm64）** 在 KunPeng 本地计算：如"关节电流 > 阈值 → 本地急停 + 上报告警"，断网时仍能自治，不等云端往返。
- **断网本地缓存**：遥测先写本地缓冲（SQLite 环形缓冲 / 文件），网络恢复按时间戳补传，保证数据零丢失、影子最终一致；受端侧/边存储限制，先做"QoS1 + 重连重发"，环形缓冲作进阶。

### 11.4 时序可观测（InfluxDB + Grafana，均 arm64）
- 遥测管线：`端上报 → EMQX → eKuiper 规则 → InfluxDB(时序库) → Grafana(看板)`。
- **看板维度**：设备健康（在线/离线/固件版本）、实时功耗/电量、CPU/内存负载、相机帧率、关节电流趋势、任务成功率、遥测告警面板。
- 价值：把"机器人跑得怎么样"从"凭感觉"变成"有指标、可回溯、可告警"，是企业最看重的工程成熟度。

### 11.5 OTA 远程固件升级（全生命周期闭环）
- **ESP32-S3**（先落地）：`esp_https_ota` 从云端/边拉取**签名固件**，双分区(otadata)切换，启动失败自动回滚（ESP-IDF 原生支持）。
- **STM32 ×2**（深度项，先设计后实做）：边网关经适配器下发固件分片 → **bootloader 写入备用 bank** → 校验签名(mbedTLS/tinycrypt) → 切换；异常回滚，防变砖。
- **管理面**：云端 IoT 平台（阿里云 IoT）做版本管理、灰度发布（先小批量）、失败回滚、升级进度可视。
- **安全**：固件必须签名校验（私钥签名/公钥验签），防止刷入恶意固件。

### 11.6 远程监控大屏
- **首选阿里云 IoT 控制台**：设备列表/地图、实时状态、控制面板（远程下发导航/抓取指令）、规则引擎（遥测→告警→微信/邮件/钉钉通知），现成且免运维。
- **自研 FastAPI + Grafana 看板**：KunPeng 本地跑，复用你的 Web 能力，替代重体量的 ThingsBoard；手机/网页既可直接 WebSocket 遥控，也可经云端平台远程查看与管控，实现"人在外地也能看机器人干活、收告警"。
